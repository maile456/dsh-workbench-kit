# 工程修改与验证

先读取项目指令、当前差异和相关构建配置。确认框架、包管理器与现有验证入口，复用仓库的做法。保护用户尚未提交的修改；只修改当前任务相关文件。检索代码优先使用 `rg` 或项目已有索引。

把需求转成可观察行为。修 bug 时优先重现具体输入和实际错误；增加功能时列明正常路径与关键失败路径。需要账本时，用 `workbench_plan` 把行为标准和交付文件存在标准分开记录。

## 完成一段可验证工作

1. 定位相关调用链、数据结构和测试，基于证据选择修改位置。
2. 实现最小完整改动，沿用仓库抽象，避免附带重构。
3. 运行针对改动的检查。复杂逻辑、数据兼容性或故障修复应有覆盖真实行为的测试；简单文案、样式微调不强制新增测试。
4. 查看真实输出和退出状态。失败时区分改动引入的问题、原有问题与环境问题，再采取相应修复。
5. 按仓库要求完成类型检查、构建或相关集成检查。已有充分证据后停止扩大测试范围。

`workbench_verify` 运行可执行文件及参数数组，并将结果关联到具体 `criterion`。对于包管理器脚本，使用当前平台可执行入口；先核对脚本存在。不要把命令文本或用户提示拼进 shell。测试目录、临时数据和写入路径都应位于当前项目允许范围。

## 成果检查

查看最终 diff 是否符合需求，确认没有调试残留、误删或意外生成文件。UI 改动在具备浏览器或视觉工具时实际打开页面验证交互和布局。仅截图不能代替业务行为测试；仅构建成功也不能证明页面可用。

将需要交付的代码、补丁或报告登记为产物，保存精确的验证命令与结果。若后续修改影响已通过的标准，重跑相关检查并更新产物记录，再完成账本。审查任务只交付发现和依据，不把建议误写成已实施改动。

复杂子任务可在用户允许且 `codex_start` 可用时交给 Codex，明确负责目录、验收标准和访问模式；避免两个代理同时修改同一批文件。接回结果后由当前会话检查 diff 并验证，不把子代理的“完成”直接当作最终验收。
